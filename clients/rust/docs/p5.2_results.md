# Phase 5.2 — Korrekte Partial-Writes und disk-backed Write-Buffer für große Dateien

## Ausgangssituation

Am Ende von Phase 5.1 war als offener Punkt dokumentiert:

> **`write()` truncation auf `O_WRONLY`**: Wenn eine Datei write-only geöffnet wird
> und nur ein Teil geschrieben wird, gehen die restlichen Bytes verloren.

Analyse des bestehenden Codes ergab zwei Teilprobleme:

1. **Kleine/mittlere Dateien (≤ 64 MiB)**: `open()` lud beim nicht-trunkierenden Öffnen
   bereits den vorhandenen Inhalt in den RAM-Write-Buffer (`initial_content`). Partielle
   Writes waren daher für diese Dateien bereits korrekt.

2. **Große Dateien (> `CACHE_STREAM_THRESHOLD_BYTES` = 64 MiB)**: Diese werden im
   normalen `read()`-Pfad via HTTP-Range-Requests bedient und nie in den Disk-Cache
   geschrieben. Bei einem schreibenden `open()` landete ihr Inhalt nach einem
   `DownloadFile`-Task zwar auf der Festplatte (im Disk-Cache), wurde dann aber als
   vollständiger `Vec<u8>` in den RAM-Write-Buffer geladen. Bei Dateien nahe oder über
   mehreren Hundert MiB drohte dabei OOM. Außerdem blieb der gesamte Dateiinhalt für
   die gesamte Dauer der offenen Handle im RAM.

## Implementierte Lösung

### 1. Disk-backed Write-Buffer (`WriteEntry::write_tmp`)

`WriteEntry` in `fuse_ops.rs` erhielt ein neues Feld:

```rust
write_tmp: Option<std::path::PathBuf>,
```

Wenn `write_tmp = Some(path)`, zeigt das Feld auf eine temporäre Datei im Verzeichnis
`~/.cache/gdrive-fuse-rs/write-tmp/<fh>.write`. In diesem Modus bleibt `content` leer;
alle Schreiboperationen gehen direkt in die Datei.

### 2. `ObjectManager`: write-tmp-Infrastruktur

In `object_manager.rs` wurden folgende Änderungen vorgenommen:

- **Neues Feld `write_tmp_dir: PathBuf`** in `ObjectManager`.
  Pfad: Geschwisterverzeichnis zum `content/`-Cache-Dir,
  z. B. `~/.cache/gdrive-fuse-rs/write-tmp/`.

- **Startup-Cleanup**: Bei jedem Mount werden liegengebliebene `*.write`-Dateien aus
  einem eventuellen Crash der vorherigen Session automatisch gelöscht.

- **`pub fn write_tmp_dir(&self) -> &Path`**: Gibt das Write-Tmp-Verzeichnis zurück.

- **`pub fn clone_disk_content_to_path(&self, file_id, dest) -> bool`**: Kopiert eine
  Datei aus dem Disk-Cache nach `dest`, ohne die Bytes in den Prozessspeicher zu laden
  (nutzt auf Linux den `copy_file_range`-Syscall via `std::fs::copy`). Wird von `open()`
  genutzt, um den Write-Buffer zu seeden.

### 3. `open()`: Branch für große Dateien

In `open()` wird jetzt die Dateigröße aus den gecacheten Metadaten gelesen. Für Dateien
> 64 MiB wird der disk-backed Pfad aktiviert:

```
Datei > 64 MiB && open() schreibend?
├─ O_TRUNC: Leere temp-Datei anlegen (kein Download nötig).
└─ Kein O_TRUNC:
   ├─ Disk-Cache-Treffer? → clone_disk_content_to_path() (kein RAM, O(Dateigröße) I/O)
   ├─ Kein Cache-Treffer?
   │  ├─ DownloadFile-Task ausführen (lädt Datei in Disk-Cache)
   │  └─ clone_disk_content_to_path() erneut versuchen
   └─ Inhalt nicht verfügbar? → leere temp-Datei + Warnung (Datenverlust möglich)
```

Das WriteEntry erhält `write_tmp = Some(tmp_path)`, `content = Vec::new()`.

### 4. `write()`: seek + write auf temp-Datei

Wenn `entry.write_tmp.is_some()`:

```rust
OpenOptions::new().write(true).open(tmp_path)?
  .seek(SeekFrom::Start(offset))?
  .write_all(data)?
```

Schreiben an beliebigem Offset hinter dem Dateiende erzeugt automatisch einen mit
Nullen gefüllten Gap (POSIX sparse-write-Semantik), identisch zum RAM-Buffer-Verhalten
(`resize(end, 0)` + `copy_from_slice`).

### 5. `flush()` / `fsync()`: No-op für disk-backed Handles

Beim schreibgeschützten Snapshot zur Crash-Recovery (write-back-Modus) wird
`store_content_at_key` nur noch für RAM-Buffer-Handles aufgerufen. Disk-backed Handles
überspringen den Snapshot, da der Inhalt bereits persistent auf der Festplatte liegt.

### 6. `release()`: temp-Datei lesen + aufräumen

```rust
let content = if let Some(ref tmp_path) = write_tmp {
    let data = std::fs::read(tmp_path)?;
    std::fs::remove_file(tmp_path);
    data
} else {
    content
};
// → content wird danach einheitlich an write_local_dirty / upload übergeben
```

Der Upload selbst erfolgt unverändert — ein kurzes Laden des Inhalts in den RAM ist
beim Hochladen zu Drive unvermeidlich.

### 7. `setattr(size)`: Truncation auf temp-Datei

```rust
if let Some(ref tmp_path) = entry.write_tmp {
    std::fs::OpenOptions::new().write(true).open(tmp_path)?
        .set_len(new_size)?;
} else {
    entry.content.resize(new_size as usize, 0);
}
```

## Speichereffizienz-Analyse

| Dateigröße | Vorher (RAM) | Nachher |
|---|---|---|
| ≤ 4 KiB | RAM-Buffer (sofort) | unverändert |
| 4 KiB – 64 MiB | RAM-Buffer (nach Download) | unverändert |
| > 64 MiB, O_TRUNC | leerer RAM-Buffer | leere temp-Datei |
| > 64 MiB, kein Trunc | **vollständig in RAM** (OOM-Risiko) | **temp-Datei im Disk-Cache** |

Für 64-MiB+-Dateien wird der Prozessspeicher während der Write-Session nur noch kurz
beim Download (DownloadFile-Task) und beim Upload in `release()` beansprucht.

## Fazit

- **Partial-Writes auf `O_WRONLY`** sind für alle Dateigrößen korrekt: `open()` seeded
  den Write-Buffer (RAM oder Disk) mit dem vorhandenen Inhalt, bevor die ersten Bytes
  überschrieben werden.
- **Kein OOM-Risiko** mehr bei großen Dateien: Während der Schreibsession werden
  > 64-MiB-Inhalte ausschließlich auf der Festplatte gehalten.
- **Robustheit bei Crashes**: Liegengebliebene `*.write`-Dateien werden beim nächsten
  Mount automatisch bereinigt.
