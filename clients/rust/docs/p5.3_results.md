# Phase 5.3 — Korrektes Read-Modify-Write für partielle O_WRONLY-Schreibvorgänge

## Problem

Wenn eine bestehende Datei mit `O_WRONLY` (ohne `O_TRUNC`) geöffnet wird und
`write()` nur einen Teilbereich überschreibt, darf der Rest der Originaldatei
**nicht** verloren gehen.

Ursprüngliche Situation vor Phase 5.2:

```
open("file.txt", O_WRONLY)         # 1 000 Bytes auf Drive
write(fh, offset=0, "hello\n", 6)  # write_buffers hat jetzt nur 6 Bytes
release(fh)                        # upload: 6 Bytes → Datei wird auf 6 B gekürzt
```

## Lösung: Read-Modify-Write in `open()`

Der Fix wurde als Teil von Phase 5.2 implementiert.  Der korrekte Ort für den
Basisinhalt-Load ist `open()`, nicht `write()`, weil:

- Ein einzelner Dateihandle kann mehrere `write()`-Aufrufe an verschiedenen Offsets
  erhalten — der Download darf nur einmal stattfinden.
- `O_TRUNC` ist ein `open()`-Flag, nicht ein `write()`-Flag; es ist sauber, die
  Entscheidung an einem Ort zu treffen.
- Der Download blockiert im FUSE-Callback-Thread — bei `write()` würde das die
  Schreibleistung für den ersten Write-Aufruf spürbar verschlechtern.

## Implementierungsdetails

### Entscheidungsbaum in `open()` (`fuse_ops.rs`)

```
open(ino, O_WRONLY | O_RDWR)
│
├─ O_TRUNC gesetzt?
│  └─ Ja → leerer Buffer (kein Download nötig)
│
└─ Kein O_TRUNC → Read-Modify-Write
   │
   ├─ Dateigröße > 64 MiB (CACHE_STREAM_THRESHOLD_BYTES)?
   │  │  Disk-backed Write-Buffer (Phase 5.2)
   │  ├─ Disk-Cache-Treffer → clone_disk_content_to_path()   (kein RAM)
   │  ├─ Cache-Miss → DownloadFile-Task → clone_disk_content_to_path()
   │  └─ Download fehlgeschlagen → leere temp-Datei + WARN
   │
   └─ Dateigröße ≤ 64 MiB — RAM Write-Buffer
      ├─ RAM-Cache-Treffer (≤ 4 KiB) → Arc::unwrap_or_clone()
      ├─ Disk-Cache-Treffer (4 KiB–64 MiB) → read_full_disk_content()
      ├─ Cache-Miss → DownloadFile-Task → nochmals RAM + Disk prüfen
      └─ Download fehlgeschlagen → Vec::new()
```

### `write()` — pufferübergreifendes Schreiben

RAM-Buffer:
```rust
let start = offset as usize;
let end   = start + data.len();
if end > entry.content.len() {
    entry.content.resize(end, 0);   // sparse gap mit Nullen füllen
}
entry.content[start..end].copy_from_slice(data);
```

Disk-backed Buffer (große Dateien):
```rust
let mut f = OpenOptions::new().write(true).open(tmp_path)?;
f.seek(SeekFrom::Start(offset))?;
f.write_all(data)?;   // Kernel füllt sparse gaps automatisch
```

In beiden Fällen werden Bytes außerhalb des geschriebenen Bereichs unverändert
beibehalten — genau die gewünschte Semantik für partielle Overwrites.

### CAS-Bypass in `write_local_dirty()`

Dirty-Inhalte werden stets unter `file_id` gespeichert, nicht unter dem MD5-Hash.
Der `cache_key_for()`-Mechanismus aus Phase 5 (CAS) wird durch `store_content_at_key()`
umgangen, da der `is_dirty`-Flag in SQLite erst am Ende von `write_local_dirty()` gesetzt
wird — `cache_key_for()` würde zu diesem Zeitpunkt noch den alten (sauberen) MD5
zurückgeben und damit den CAS-Invarianten korrumpieren.

## Verhaltensvorgaben im Überblick

| Kommando | Shell-Flags | Ergebnis |
|---|---|---|
| `echo "test" > file.txt` | `O_WRONLY\|O_CREAT\|O_TRUNC` | Datei auf 5 Bytes gekürzt ✓ |
| `printf "XX" \| dd bs=2 seek=5 of=file.txt conv=notrunc` | `O_WRONLY` (kein `O_TRUNC`) | Nur Bytes 5–6 überschrieben, Rest bleibt ✓ |
| `truncate -s 0 file.txt` | `O_WRONLY\|O_TRUNC` | Datei auf 0 Bytes ✓ |
| Editor speichert Datei | `O_WRONLY\|O_CREAT\|O_TRUNC` | Komplette Überschreibung ✓ |
