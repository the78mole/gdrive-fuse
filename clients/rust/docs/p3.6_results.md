# Phase 3.6 — Metadata-Stabilisierung (Nemo-Icon-Flackern)

## Problem

PDF-Icons in Nemo flackern kontinuierlich. `evince-thumbnailer` ruft `getattr`
auf, sieht jedes Mal eine andere `mtime`, hält die Datei für verändert und bricht
seinen `read`-Versuch ab — was das Flackern auslöst.

## Root-cause-Analyse

### Issue 1 — Unstabile Zeitstempel (`mtime`/`ctime`/`atime`)

`make_file_attr` in `object_manager.rs` rief `SystemTime::now()` für alle drei
Zeitfelder auf. Da FUSE `getattr` pro Dateizugriff aufruft, bekam jede Abfrage
eine andere Nanosekunden-genaue Zeit — obwohl sich der Dateiinhalt nicht änderte.
`evince-thumbnailer` wertet `mtime` aus, um festzustellen, ob es seinen Cache
ungültig machen muss; die ständige Änderung zwang es zu einem Neustart-Loop.

### Issue 2 — Unstabile Inodes nach Neustart

`store_metadata` enthielt `ON CONFLICT DO UPDATE SET inode = excluded.inode`.
Beim Neustart des Daemons ohne gespeicherte Inode-Map wurden neue Inode-Nummern
vergeben, während SQLite trotzdem die alten überschrieb. Außerdem wurde die
SQLite-Inode-Map beim Start nicht wiederhergestellt, sodass jede neue Session
mit Inode 2 begann.

### Issue 3 — Fehlender EOF-Guard in `read`

Bei einem `read`-Aufruf mit `offset >= file_size` (z. B. nach einem geclampten
letzten Block) fehlte eine explizite Rückgabe. Die Abfrage fiel durch zu einem
potenziellen HTTP-Download statt einer leeren Antwort.

## Fixes

### Fix 1 — `parse_mtime` + stabile Zeitstempel (`object_manager.rs`)

Neue freie Funktion `parse_mtime(s: &str) -> SystemTime`:

```rust
pub fn parse_mtime(s: &str) -> SystemTime {
    if s.is_empty() { return UNIX_EPOCH; }
    DateTime::parse_from_rfc3339(s)
        .ok()
        .and_then(|dt| u64::try_from(dt.timestamp()).ok())
        .map(|secs| UNIX_EPOCH + Duration::from_secs(secs))
        .unwrap_or(UNIX_EPOCH)
}
```

`FileInfo.modified_time` ist ein RFC3339-String aus der Google-Drive-API
(`#[serde(default)]` → leerer String für Ordner/Workspace-Dateien →
`UNIX_EPOCH`, stabil). Die Konvertierung auf Sekundengenauigkeit garantiert
deterministische, identische Werte für identische Eingaben.

`make_file_attr` ersetzt `SystemTime::now()` durch `parse_mtime(&info.modified_time)`
für alle drei Zeitfelder (`atime`, `mtime`, `ctime`).

### Fix 2 — Inode-Stabilität (`db_manager.rs` + `object_manager.rs`)

**`db_manager.rs`** — `store_metadata` SQL: `inode` aus dem `UPDATE SET`-Abschnitt
entfernt:

```sql
ON CONFLICT(remote_id) DO UPDATE SET
    parent_id    = excluded.parent_id,
    last_fetch   = excluded.last_fetch,
    md5_checksum = excluded.md5_checksum,
    is_dirty     = excluded.is_dirty
-- inode intentionally omitted: once assigned it must never change
```

Neue Methode `load_inode_map()` liest alle `(remote_id, inode)`-Paare aus SQLite.

**`object_manager.rs`** — `new_with_disk_dir_and_db` stellt beim Start die
Inode-Map aus SQLite wieder her:

```rust
let mut max_restored_ino: u64 = ROOT_INO;
if let Some(db_ref) = &db {
    for (remote_id, inode) in db_ref.load_inode_map() {
        if inode < ROOT_INO || remote_id.is_empty() { continue; }
        id_to_ino.entry(remote_id.clone()).or_insert(inode);
        ino_to_id.entry(inode).or_insert(remote_id);
        if inode > max_restored_ino { max_restored_ino = inode; }
    }
}
next_ino: AtomicU64::new(max_restored_ino + 1),
```

Dasselbe Drive-File bekommt nach einem Neustart dieselbe Inode-Nummer.

### Fix 3 — EOF-Guard in `read` (`fuse_ops.rs`)

```rust
let known_size = self.obj.get_metadata(&file_id).map(|f| f.size).unwrap_or(u64::MAX);
if offset >= known_size {
    reply.data(&[]);
    return;
}
```

Fallback `u64::MAX` bedeutet "Größe unbekannt → nicht überspringen" (sicherer
Standard).
