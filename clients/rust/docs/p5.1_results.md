# Phase 5.1 — Bug-Fix: Rename-Timeout & veralteter Name-Index

## Übersicht

Nach Phase 5 traten zwei Fehler auf, wenn ein Verzeichnis auf dem FUSE-Mount
gelöscht und danach der gleiche Ordner erneut hineinkopiert wurde:

1. **„Möchten Sie überschreiben?"-Dialog** — der Dateimanager (GIO/Nautilus)
   zeigte einen Konfliktdialog, obwohl das Zielverzeichnis vorher erfolgreich
   gelöscht wurde.
2. **Upload-Timeout / Hänger** — der Upload brach mit dem Fehler
   `rename: timed out waiting for upload of '__pending__2'` ab.

Beide Fehler wurden in dieser Phase behoben.  
66/66 Tests bestehen; `cargo clippy -- -D warnings` ist sauber.

---

## 1. Root-Cause-Analyse

### Bug 1: veralteter `name_index` nach `rmdir`/`unlink`

`invalidate_dir(parent_id)` entfernte bislang nur den `dir_cache`-Eintrag,
ließ aber alle zugehörigen `name_index`-Einträge stehen.

Ablauf:
```
mkdir "ADR035"  → Drive-ID "XYZ" in dir_cache + name_index
rmdir "ADR035"  → invalidate_dir: dir_cache["root"] entfernt
                  name_index["root:ADR035"] = "XYZ"  ← blieb stehen!
mkdir "ADR035"  → neues __pending__ angelegt
lookup "ADR035" → name_index-Fallback findet alte Drive-ID "XYZ"
                  → Kernel sieht Konflikt → Dateimanager fragt nach Überschreiben
```

### Bug 2: Rename-Timeout beim GIO-Schreibmuster

GIO/Nautilus schreibt Dateien nach folgendem Muster:
```
create(".goutputstream-XXXX")    # temporärer Name → __pending__<fh>
write(...)
rename(".goutputstream-XXXX", "finale_datei.txt")   # rename VOR release()!
release()                                            # → löst Upload aus
```

Der alte Code in `rename()` wartete nach dem Erkennen eines `__pending__`-Eintrags
bis zu 60 Sekunden darauf, dass `replace_pending_id()` die echte Drive-ID
einträgt.  Diese Funktion wird aber erst von `release()` aufgerufen — welches
seinerseits **nach** dem `rename()` kommt.  Das Warten lief daher immer in den
Timeout.

## 2. Änderungen

### 2.1 `src/object_manager.rs` — `invalidate_dir` bereinigt den `name_index`

**Vorher:** `dir_cache`-Eintrag wurde entfernt, `name_index` blieb unverändert.

**Nachher:** Nach dem Entfernen des `dir_cache`-Eintrags werden alle
enthaltenen Dateien iteriert und ihre `name_index`-Schlüssel gelöscht — mit
Ausnahme von `__pending__`-Platzhaltern, die `rename()` noch benötigen kann,
während der Upload noch aussteht.

```rust
pub fn invalidate_dir(&self, parent_id: &str) {
    if let Some((_, entry)) = self.dir_cache.remove(parent_id) {
        for f in entry.files.iter() {
            if !f.id.starts_with("__pending__") {
                let key = make_name_key(parent_id, &f.name, &f.mime_type);
                self.name_index.remove(&key);
            }
        }
    }
    debug!("invalidate_dir('{}')", parent_id);
}
```

### 2.2 `src/object_manager.rs` — neue Methode `rename_pending()`

Neue öffentliche Methode, die einen `__pending__`-Platzhalter umbenennt und
optional in ein anderes Elternverzeichnis verschiebt, **ohne** auf den
abgeschlossenen Upload zu warten:

```rust
pub fn rename_pending(
    &self,
    old_parent_id: &str,
    new_parent_id: &str,
    pending_id: &str,
    new_name: &str,
)
```

Schritt-für-Schritt:
1. Alten `name_index`-Eintrag (`old_parent_id:old_name`) entfernen.
2. `metadata[pending_id].name` auf `new_name` aktualisieren.
3. Neuen `name_index`-Eintrag (`new_parent_id:new_name`) eintragen.
4. Elternverzeichnis geändert → Placeholder aus dem alten `dir_cache`-Eintrag
   entfernen und in den neuen verschieben.  Sonst: `name` in-place im alten
   `dir_cache`-Eintrag aktualisieren.

### 2.3 `src/fuse_ops.rs` — `rename()` Sofortpfad für Pending-Dateien

**Vorher:** 60-Sekunden-Busy-Wait auf `ino_to_drive_id()` ≠ `__pending__`.

**Nachher:** Für `__pending__`-IDs wird kein Drive-API-Aufruf getätigt und
nicht gewartet.  Stattdessen:

```rust
if raw_file_id.starts_with("__pending__") {
    let fh_val: u64 = raw_file_id
        .strip_prefix("__pending__")
        .and_then(|s| s.parse().ok())
        .unwrap_or(u64::MAX);
    // WriteEntry aktualisieren: release() verwendet den neuen Namen/Parent.
    if let Some(mut wb) = self.write_buffers.get_mut(&fh_val) {
        wb.name = newname_str.to_string();
        if parent_id != newparent_id {
            wb.parent_id = newparent_id.clone();
        }
    }
    // dir_cache und name_index sofort synchron halten.
    self.obj.rename_pending(&parent_id, &newparent_id, &raw_file_id, &newname_str);
    reply.ok();
    return;
}
```

Wenn `release()` später feuert, liest `write_local_dirty()` Name und Parent
aus dem bereits aktualisierten `WriteEntry` und erstellt die Datei auf Drive
mit dem korrekten Ziel.

## 6. Nachfolgende Fehleranalyse (Neustart-404-Schleife)

### Symptom

Nach einem Neustart des Clients lieferte der `UploadManager` sofort 404-Fehler
für 18 schmutzige Einträge aus der vorherigen Sitzung:

```log
upload-manager: 18 dirty entry/entries to upload
upload-manager: create_file '04_passive_buzzer.py': HTTP status client error (404 Not Found) — will retry
upload-manager: create_file '05_laser.py': HTTP status client error (404 Not Found) — will retry
…
```

Beim nächsten Neustart dieselben 18 Fehler → Endlosschleife.

### Root-Cause

Die schmutzigen Einträge in der SQLite-`metadata`-Tabelle hatten eine
`parent_id`, die auf einen Drive-Ordner zeigt, der **in der vorherigen
Sitzung gelöscht** wurde (Delete + Re-Copy-Muster).  
Beim Neustart versucht `UploadManager::upload_entry` `create_file(parent_id =
deleted_folder_id)` → Drive antwortet mit 404 → Fehler geloggt, dirty-Flag
bleibt gesetzt → gleicher Fehler beim nächsten Start.

Zweite Variante (defensiv abgedeckt): `parent_id` enthält noch `__pending__<N>` weil der
Elternordner selbst noch nicht auf Drive hochgeladen wurde.  
Da `mkdir` synchron ist, tritt dieser Fall unter normalen Bedingungen nicht auf,
aber kann bei abgebrochenen Sitzungen in der DB stehen bleiben.

### Änderungen

#### `src/db_manager.rs` — neue Methode `abandon_dirty_entry()`

Löscht einen dirty-Eintrag permanent aus der `metadata`-Tabelle.  
Wird nur aufgerufen, wenn der Upload nachweislich unwiederherstellbar ist
(HTTP 404 auf `create_file`).

```rust
pub fn abandon_dirty_entry(&self, remote_id: &str) {
    // DELETE FROM metadata WHERE remote_id = ?1 AND is_dirty = 1
    …
    warn!("db: abandoned unrecoverable dirty entry '{}'", remote_id);
}
```

#### `src/upload_manager.rs` — Hilfsfunktion `is_http_not_found()`

Erkennt einen HTTP-404-Fehler aus einem `anyhow::Error`-Wrapping über
`reqwest::Error::status()`:

```rust
fn is_http_not_found(e: &anyhow::Error) -> bool {
    e.downcast_ref::<reqwest::Error>()
        .and_then(|re| re.status())
        .map(|s| s == reqwest::StatusCode::NOT_FOUND)
        .unwrap_or(false)
}
```

#### `src/upload_manager.rs` — `upload_entry()` — zwei Guards im `is_new`-Zweig

**Guard 1 — Pending parent**: Wenn `meta.parent_id.starts_with("__pending__")`,
wird der Eintrag für diesen Zyklus übersprungen (defer):

```rust
if meta.parent_id.starts_with("__pending__") {
    warn!("upload-manager: deferring '{}' — parent '{}' is still pending", …);
    return;
}
```

**Guard 2 — HTTP 404 abandon**: Wenn `create_file` mit 404 schlägt, wird
`abandon_dirty_entry` aufgerufen statt das dirty-Flag stehen zu lassen:

```rust
Err(e) => {
    if is_http_not_found(&e) {
        error!("…parent '{}' not found on Drive (404) — abandoning…", meta.parent_id);
        self.db.abandon_dirty_entry(remote_id);
        self.obj.remove_pending_from_dir(&meta.parent_id, remote_id);
    } else {
        error!("…will retry");
    }
}
```
